## 3. إنشاء قاعدة بيانات Supabase من SQL

1. افتح Supabase، أنشئ Organization/Project **جديدًا**، واحفظ كلمة مرور قاعدة البيانات في مدير كلمات المرور. هذه كلمة مرور إدارة الخدمة، وليست كلمة مرور دخول الموقع.
2. انتظر اكتمال إنشاء المشروع. افتح **SQL Editor → New query**.
3. افتح `sql/01-install.sql` في محرر نصوص، انسخ محتواه كاملًا والصقه ثم اضغط Run. ينشئ المخطط `union_private` والجداول والفهارس والقيود والحماية.
4. هذا الملف يعمل **مرة واحدة على مشروع جديد**. إذا ظهر خطأ بأن المخطط موجود، توقف وتحقق من المشروع؛ لا تحذف قاعدة قد تحتوي بيانات. كل التنصيب ضمن transaction، فإذا فشل لا تعتبره مكتملًا.
5. افتح Query جديدة وشغّل `sql/02-storage.sql`. ثم افتح Storage وتحقق أن bucket باسم `showroom-logos` **Private**، والحد 2 MiB وصيغة PNG فقط. لا تضف سياسات قراءة أو رفع عامة. لا تعدل مخططات Supabase الداخلية أو جدول ترحيلاته.
6. من إعدادات Data API لا تضف `union_private` إلى قائمة exposed schemas. البرنامج يستخدم اتصال PostgreSQL من الخادم وليس واجهة Data API.

**Firebase:** هذه النسخة تعتمد PostgreSQL؛ لا يمكن لصق SQL في Cloud Firestore لتشغيلها. اختيار Supabase هو المسار المدعوم هنا. تحويلها إلى Firestore يحتاج تنفيذًا واختبارات مختلفة، ولا توجد في الملف موصلات توهم أنها جاهزة لذلك.

## 4. إنشاء الأسرار وحساب قاعدة بيانات محدود

من الطرفية:

```sh
node scripts/generate-secrets.mjs
```

ينشئ ملفًا محليًا `.env.secrets` مرة واحدة، ولا يطبع القيم. افتحه محليًا واحفظ القيم في مدير كلمات المرور. لا ترسله مع النسخة ولا ترفعه إلى المستودع. يشمل:

- `AUTH_SECRET`: ثابت لتجزئة كلمات المرور وتشفير مفاتيح المصادقة؛ فقدانه قد يمنع الدخول بعد الاستعادة.
- `ADMIN_CLI_SECRET`: مفتاح تهيئة/استعادة الإدارة، ليس للاستخدام اليومي.
- `RUNTIME_DB_PASSWORD`: كلمة مرور اتصال التطبيق بالداتا بيز.
- `BOOTSTRAP_ADMIN_PASSWORD`: كلمة مرور أولية قوية، **16** محرفًا فيها أحرف كبيرة وصغيرة ورقم ورمز، وفق المتطلبات المتفق عليها.

لتهيئة الدور `union_app` الذي أنشأه SQL، اختر أحد المسارين:

**المسار البسيط في SQL Editor:** استبدل النص التوضيحي بكلمة المرور المولدة `RUNTIME_DB_PASSWORD`، وشغّل:

```sql
ALTER ROLE union_app LOGIN PASSWORD 'PASTE_THE_GENERATED_RUNTIME_PASSWORD_HERE';
```

لا تشغل المثال كما هو. كلمة المرور المولدة تستخدم أحرفًا مناسبة للاقتباس. لا تحفظ هذه Query في مستودع الكود ولا ترسل لقطة تعرض القيمة. لا تستخدم `postgres` لاتصال التطبيق اليومي.

**مسار فريق التنصيب:** ضع مؤقتًا `ADMIN_DATABASE_URL` من اتصال **Direct أو Session pooler** و`RUNTIME_DB_PASSWORD` في ملف `.env` المحلي، ثم `npm run db:role`. السكربت يقتبس كلمة المرور داخل PostgreSQL ويتحقق من TLS. احذف `ADMIN_DATABASE_URL` و`RUNTIME_DB_PASSWORD` من بيئة النشر بعد ذلك. إذا احتاج المزود شهادة CA فضعها في `DATABASE_CA_PEM`.

من زر **Connect** في Supabase اختر **Transaction pooler**، غالبًا المنفذ **6543**، لموقع Vercel. انسخ المضيف والمنفذ ومرجع المشروع كما يعرضها مشروعك، ثم استخدم اسم المستخدم `union_app.PROJECT_REF` بدل `postgres.PROJECT_REF`. استبدل كلمة المرور بكلمة `RUNTIME_DB_PASSWORD`، وليس بكلمة مرور حساب الأدمن في الموقع. مثال توضيحي:

```text
postgresql://union_app.PROJECT_REF:ENCODED_PASSWORD@EXACT_POOLER_HOST:6543/postgres
```

لا تخمّن اسم المضيف أو المنطقة. عند استخدام كلمة مرور تتضمن رموزًا محجوزة في URL يجب ترميزها percent-encoding. القيمة المولدة من سكربتنا لا تحتوي تلك الرموز. لا تستخدم prepared statements مسماة مع Transaction pooler؛ موصل هذه النسخة يرسل استعلامات غير مسماة.

## 6. نشر الموقع على Vercel

1. ارفع المصدر إلى GitHub الخاص. فعّل حماية الفرع الأساسي وحصر الوصول بفريق التنصيب.
2. في Vercel اختر **Add New → Project → Import Git Repository**، واختر المستودع.
3. Framework هو **Next.js**، وRoot Directory المجلد المحتوي `package.json`. Build Command: `npm run build`. Install Command: `npm ci`. اترك Output Directory للإعداد الافتراضي. اختر Node 22.
4. أضف متغيرات البيئة من الجدول. استخدم `APP_ENV=staging` مبدئيًا. استبعد بيانات `BOOTSTRAP_ADMIN_*` من Vercel؛ يحتاجها سكربت جهازك فقط. لا تنشر اتصال `ADMIN_DATABASE_URL` على Vercel.
5. حدد عنوان Production الذي ستستخدمه، مثل العنوان المخصص للمشروع على Vercel، وضعه في `APP_ORIGIN`. انشر ثم تحقق من تطابقه مع العنوان الذي تفتحه. لا تستخدم عنوان preview متغيرًا كـ canonical للموقع الحقيقي.
6. ضع Preview Deployments وراء **Deployment Protection** المتاحة لخطة الفريق. استخدم مشروع Supabase منفصلًا للتجربة. لا تورّث أسرار production لفرع تجريبي.
7. بعد تعديل أي متغير يؤثر في البناء، مثل `APP_ORIGIN` أو `APP_ENV`، اعمل **Redeploy**؛ الملف المبني يحتوي metadata وrobots الناتجة عن هذه القيم.

لا يكفي رفع الملفات إلى استضافة static أو cPanel دون Node.js: الموقع يحتوي API وقاعدة بيانات ويحتاج خادم Next.js أو استضافة تدعمه. للتشغيل على خادم Node مستقل: `npm ci && npm run build` ثم `npm start` خلف reverse proxy يدعم HTTPS ويضبط `Host` و`X-Forwarded-Proto` و`X-Forwarded-For` ويستبدل أي قيم مرسلة من العميل. لا تعرض منفذ Node أو PostgreSQL مباشرة للإنترنت.

## 7. إنشاء الأدمن وإغلاق التهيئة

1. في `.env` المحلي ضع `APP_ORIGIN` الخاص بالنشر، والمفتاح المطابق `ADMIN_CLI_SECRET`، وبيانات أول أدمن. يجب أن تكون بيئة النشر مؤقتًا `ADMIN_CLI_ENABLED=true`.
2. نفّذ `npm run admin:create`. إنشاء أول أدمن مسموح فقط عند عدم وجود أدمن سابق، ويوجد قيد قاعدة يمنع إنشاء أدمنين متزامنين.
3. افتح رابط `/admin` **بنفسك** وسجّل الدخول. فعّل التحقق بخطوتين من **أمان حسابي** واحفظ رموز الاسترداد في مدير كلمات المرور. كل رمز يُستهلك مرة واحدة. بعد التفعيل يسجل النظام خروج الجلسات.
4. غيّر `ADMIN_CLI_ENABLED=false` في Vercel، واحذف `ADMIN_CLI_SECRET` من النشر إن لم تكن تحتاجه، واحذف بيانات تهيئة الأدمن من ملف التشغيل اليومي. أعد النشر.
5. أثناء الإغلاق يرجع `/api/server/admin` استجابة 404. الاستعادة مستقبلًا تحتاج إعادة تفعيل مؤقتة ومفتاحًا جديدًا ثم إغلاقًا فورًا؛ راجع `docs/OPERATIONS.md`.
6. فعّل قواعد جدار حماية Vercel وحدود الطلبات المناسبة لمسارات الدخول والحجز. عدّادات التطبيق تعمل من قاعدة البيانات وعبر مثيلات الخادم، لكنها ليست بديلًا عن حماية DDoS لدى الاستضافة.

لا توجد كلمة مرور `admin2005` أو حسابات تجريبية مزروعة في SQL. كل معرض/موظف جديد يحصل على كلمة مرور مستقلة، ولا تستخدم كلمة مشتركة لجميع الحسابات.

| من يستخدم الرابط؟       | الرابط                         |
| ----------------------- | ------------------------------ |
| العملاء والحجز          | `https://YOUR_DOMAIN/`         |
| روابط المعارض فقط       | `https://YOUR_DOMAIN/portals`  |

## 9. ربط الدومين والظهور في البحث

اشترِ الدومين باسمك. في **Vercel → Project → Settings → Domains** أضفه، ثم في مزود DNS طبّق **السجلات التي يعرضها Vercel** بدل نسخ قيم قديمة من دليل. اختر نطاقًا أساسيًا واحدًا وحوّل النسخة الأخرى إليه. بعد صدور شهادة HTTPS:

1. غيّر `APP_ORIGIN` إلى النطاق الأساسي، و`APP_ENV=production`، وأعد النشر.
2. افتح `/robots.txt` و`/sitemap.xml`. الـ sitemap يحتوي صفحة العميل فقط؛ البوابات الداخلية عليها `noindex` من HTML ومن header.
3. اربط [Google Search Console](https://search.google.com/search-console/about) بالدومين وأرسل sitemap.

الفهرسة ليست مضمونة ولا فورية. `noindex` تعليمات لمحركات البحث وليس أداة صلاحيات؛ حماية البيانات من الخادم. إذا فُهرست بوابة سابقًا استخدم أداة الإزالة في Search Console وتحقق من وصول bot إلى header الجديد.

## 10. فحص التسليم قبل البيانات الحقيقية

بعد تعبئة `.env` النهائي وتشغيل الموقع:

```sh
npm run check:env
npm run check:deployment
```

الفحص الثاني يتصل بقاعدة البيانات عبر TLS ويتأكد من الدور المحدود، RLS، تفعيل MFA للأدمن وخصوصية bucket. لا يطبع الأسرار. أخطاء الاتصال تعني أن النشر لم يكتمل. أضف معرضًا فعليًا وخدمة ومستخدمين، ثم افحص:

- رفع شعار، إعادة تحميل الصفحة واسترجاعه، ثم تعديله والتحقق من حذف القديم.
- الحجز من جهازين، وتأكيد السعة وعدم تضاعف الطلب عند إعادة المحاولة بعد انقطاع الرد.
- إدارة المعرض ترى بيانات معرضها؛ موظف يرى مهامه فقط؛ طلب IDs لمعرض آخر يرجع رفض صلاحية.
- تنفيذ المهمة بملاحظة واعتماد الإنجاز، ثم تعطيل حساب والتأكد من توقف جلساته.
- تغيير كلمة مرور وتأكيدها والخروج من جميع الأجهزة؛ 3 كلمات قديمة خاطئة تقفل التحقق 15 دقيقة.
- عدم ظهور روابط الإدارة عند العميل، وفحص الهاتف واللغة العربية والإنجليزية، والـ spinner أثناء بطء الشبكة.
- تصدير قاعدة البيانات والشعارات، ثم **استعادتها في مشروع تجريبي مستقل**. ملف المصدر وحده ليس نسخة بيانات.

لا تحذف بيانات تجريبية باستخدام DELETE عشوائي. قاعدة التنصيب فارغة؛ التجارب تكون في مشروع منفصل. سجّل نتيجة قبول البيئة الفعلية لدى فريق النشر. تفاصيل نطاق الاختبارات في `docs/VALIDATION.md`، والنسخ والاستعادة في `docs/OPERATIONS.md`.

## 11. إعادة تشغيل الاختبارات المتقدمة

`npm test` يختبر SQL والصلاحيات عبر PostgreSQL مضمّن. لا يثبت وحده سباقات الاتصالات. اختبار التكامل يستخدم PostgreSQL حقيقيًا متعدد الاتصالات ويخلق قاعدة اختبار مؤقتة ويحذفها:

```sh
# PostgreSQL محلي مع صلاحية CREATE DATABASE ومستخدم إدارة للاختبار فقط:
# ضع TEST_ADMIN_DATABASE_URL في بيئة الطرفية، مثل اتصال loopback محلي.
npm run test:integration
```

السكربت يرفض المضيف البعيد، ولا تقم بإزالة هذا الحاجز. يمكن للفريق استخدام Docker محلي أو PostgreSQL مثبت، مع كلمة مرور اختبار وصلاحية منح LOGIN للدور `union_app`. لا تضع رابط production في المتغير.

لاختبار واجهة تشغيل محلية، نزّل متصفح الاختبار مرة واحدة `npx playwright install chromium`، شغّل التطبيق في طرفية أخرى، ثم `npm run test:ui`. يمكن ضبط `UI_TEST_URL` محليًا، وتمرير `UI_ADMIN_PHONE` و`UI_ADMIN_PASSWORD` لحساب **اختبار محلي** لتوسيع الفحص. تظهر اللقطات في `tests/artifacts`، وهي مستثناة من الحزمة. راجع أيضًا الفحص اليدوي للحجز الكامل، وليس الصفحات فقط.

## 12. المشاكل الشائعة

| المشكلة                 | أين تبدأ؟                                                                                          |
| ----------------------- | -------------------------------------------------------------------------------------------------- |
| خطأ اتصال PostgreSQL    | المضيف/المنفذ من Connect، اسم `union_app.PROJECT_REF`، كلمة الدور، CA؛ لا تعطل TLS لتجاوز الخطأ    |
| المعارض لا تظهر         | قاعدة جديدة فارغة؛ أضف المعرض من الأدمن ثم خدمة منشورة؛ تحقق أنه مفعّل                             |
